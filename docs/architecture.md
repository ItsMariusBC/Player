# Architecture du lecteur

Le code est organisé en couches. Une couche ne dépend que de celles situées au-dessus dans le tableau.

| Couche       | Fichiers                                                                               | Rôle                                                                                                                                                                                                                                                                                                                                                              |
| ------------ | -------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Moteur       | `lib/music-manager.ts`, `lib/queue-manager.ts`                                         | Élément `<audio>`, `AudioContext`, file de lecture (alimentée par le catalogue serveur). Émet des `PlayerEvent` (`play`, `pause`, `track`, `time`, `queue`). Ignore l'interface.                                                                                                                                                                                  |
| Contrôleurs  | `lib/playback-controller.ts`, `lib/notification-manager.ts`, `lib/shortcut-manager.ts` | `PlaybackController` est l'unique point d'entrée des actions (lecture, pause, stop, piste suivante/précédente, seek, volume). `NotificationManager` transforme les événements en une seule notification visible à la fois. `ShortcutManager` relie le clavier au contrôleur.                                                                                      |
| Composition  | `lib/player-runtime.ts`                                                                | `createPlayerRuntime()` assemble moteur, contrôleurs et raccourcis, et expose `destroy()`. C'est le seul endroit où les instances sont créées.                                                                                                                                                                                                                    |
| Présentation | `components/**`, `lib/hooks/**`                                                        | Composants React sans logique métier. `usePlaybackState(music)` fournit l'état courant ; les actions passent par `playback`. `useSongGradient(song)` fournit les couleurs du fond. Pour les admins, `AdminButton` s'affiche à côté du lien de déconnexion (`CornerActions`) et ouvre `AdminPanel` (démonte le reste de l'interface comme le visualiseur agrandi). |

## Règles

- Un composant ne modifie jamais l'état du moteur directement : il appelle `playback.*`.
- Un composant n'écoute jamais `<audio>` : il lit `usePlaybackState` ou s'abonne à `music.subscribe`.
- Les notifications sont une politique (`lib/notification-manager.ts`) et une vue (`components/song-notification.tsx`). La politique est testée sans DOM.
- Le catalogue vient de `GET /api/catalog` (`lib/catalog.ts`, `useCatalog()` : chargement au montage, toutes les 60 s et sur `refresh()`). `flattenCatalog` en tire la file : à chaque niveau, les sous-dossiers d'abord (profondeur d'abord, ordre de l'arbre) puis les titres du niveau par `position` ; les titres racine viennent donc en dernier. La liste affiche l'arbre dans ce même ordre. Médias et pochettes sont servis par `/api/media/:id` et `/api/media/:id/cover` (même origine, cookie de session). Aucun média ni `music/data.json` n'est plus versionné : le dossier `music/` et les fichiers de `public/` (hors `favicon.ico`) ont disparu, le catalogue vit dans `DATA_DIR` et s'y importe avec `yarn migrate:catalog`.
- À chaque nouveau catalogue, `queueManager.setSongs` conserve le titre courant par `id` ; s'il a disparu, la file reprend au même index. Un rafraîchissement sans changement du titre courant ne relance pas la lecture.
- Le fond dégradé est dérivé de la pochette (`lib/palette.ts`).
- Le fond est une scène React Three Fiber maison (`components/gradient/`), shaders repris de shadergradient 1.3.5 (MIT). Les couleurs sont des uniforms mutés dans la boucle de rendu : un changement de piste ne provoque ni re-render React ni recompilation de shader. Rendu à la demande à 30 i/s (`FRAMES_PER_SECOND`), `dpr` 1, sans `preserveDrawingBuffer`, chargé en chunk séparé après le premier rendu.

## Serveur et administration

Le serveur (`server/src/`, Node 24, Hono, SQLite) a ses propres couches. Une couche ne dépend que de celles situées au-dessus dans le tableau.

| Couche         | Fichiers                                                                                                                                             | Rôle                                                                                                                                                                                                                                                                                                                                                                                                |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Catalogue      | `catalog/folders.ts`, `catalog/tracks.ts`, `catalog/tree.ts`, `catalog/tx.ts`                                                                        | Dépôt SQLite des dossiers et des titres. `inTransaction` (`tx.ts`) ouvre un `SAVEPOINT`, donc les appels s'imbriquent. `tree.ts` construit l'arbre. Erreurs typées : `FolderConflictError`, `FolderCycleError`, `FolderNotEmptyError`, `NotFoundError`.                                                                                                                                             |
| Médias         | `media/storage.ts`, `media/probe.ts`, `media/image.ts`, `media/tags.ts`                                                                              | Fichiers dans `DATA_DIR/media/<trackId>/original.<ext>` et `cover.<ext>` ; dépôts en cours dans `DATA_DIR/incoming/<importId>/`. `probe.ts` détecte le format par signature (l'extension n'est jamais crue), lit les tags avec music-metadata et calcule le SHA-256 en flux. `tags.ts` écrit les tags au mieux (node-id3 pour MP3, metaflac-js pour FLAC) ; un WAV n'est jamais réécrit.            |
| Import         | `media/ingest.ts`, `admin/imports.ts`                                                                                                                | `ingestFile` est le pipeline commun (sondage, doublon par empreinte, publication, ligne SQL) ; le script de migration et la file asynchrone l'appellent. `admin/imports.ts` traite un import à la fois (chaîne de promesses, donc pas de course sur la détection de doublon).                                                                                                                       |
| Administration | `routes/admin-folders.ts`, `routes/admin-tracks.ts`, `routes/admin-imports.ts`, `routes/admin-metadata.ts`, `admin/track-edit.ts`, `admin/events.ts` | Routes sous `/api/admin/*`, réservées au groupe admin. `track-edit.ts` porte le verrou par titre (`createTrackLocks`), partagé par PATCH, DELETE, pochette et application de métadonnées. `events.ts` écrit une ligne d'audit dans `admin_events` pour chaque mutation (jamais de secret dans `detail`).                                                                                            |
| Métadonnées    | `metadata/providers.ts`, `metadata/search.ts`, `metadata/fetch-guard.ts`                                                                             | Recherche chez MusicBrainz (+ Cover Art Archive), Deezer et iTunes. Une requête par seconde et par fournisseur, imposée en attendant ; 5 s de budget par fournisseur ; propositions gardées 15 min sous des identifiants opaques. `fetch-guard.ts` télécharge les pochettes proposées (voir ci-dessous).                                                                                            |
| Demandes       | `requests/repo.ts`, `routes/requests.ts`, `routes/admin-requests.ts`                                                                                 | Demandes de sons des utilisateurs (table `song_requests`, migration 3). `repo.ts` porte les règles : limite de 20 demandes en attente par utilisateur (`RequestLimit`), doublon titre+artiste normalisé. Les routes `/api/requests*` sont ouvertes à toute session, `/api/admin/requests*` au groupe admin. La recherche de propositions réutilise l'instance `MetadataSearch` de l'administration. |

Normalisation du volume : à l'import, `media/loudness.ts` mesure le titre avec ffmpeg (filtre `ebur128`, binaire `FFMPEG_PATH`, `ffmpeg` par défaut ; l'image Docker l'embarque). Le résultat est stocké dans deux colonnes de `tracks` (migration 4) : `loudness_lufs` (loudness intégrée) et `true_peak_dbtp` (crête vraie), toutes deux `NULL` quand la mesure manque, échoue ou donne `-inf` (silence). Une mesure en échec n'empêche pas l'import. `GET /api/catalog` expose `loudnessLufs` et `truePeakDbtp`. Côté client, `lib/loudness.ts` (`replayGain`) calcule le gain en dB : cible -14 LUFS, borné à [-20, +12] dB, puis réduit pour que la crête vraie reste sous le plafond de -1 dBTP ; 0 dB si le titre n'est pas mesuré. Le lecteur applique ce gain par un `GainNode` par élément audio dans le graphe Web Audio. Toute tentative de mesure (import ou rattrapage) pose la colonne `loudness_measured_at` (migration 5) ; `NULL` = jamais tentée, et `updated_at` n'est jamais modifié (il pilote le cache des pochettes). Les titres sans mesure (import avant la migration, ou `yarn migrate:catalog`, qui ne mesure pas) se rattrapent depuis l'onglet Catalogue (« Analyser les titres restants ») : `GET /api/admin/loudness` donne `{ total, measured, failed, pending, running, available }` (`failed` : tentés sans valeur, silence ou fichier illisible, affichés « n titres sans mesure » ; `running` : passe en cours ; seul un `available` positif est mis en cache) et `POST /api/admin/loudness/backfill` démarre une passe paresseuse, un titre à la fois sur la chaîne des imports (un import déposé pendant la passe s'intercale), répond 202 `{ queued, running }` (`queued: 0` si une passe tourne déjà) et 409 `ffmpeg_unavailable` sans ffmpeg. L'interface relit l'état toutes les 2 s (requêtes chaînées) tant que `running` est vrai, puis s'arrête.

Diffusion audio : un titre ne change jamais sous un même id (seule la conversion WAV vers FLAC remplace le fichier stocké), donc `GET|HEAD /api/media/:id` est cachable : `Cache-Control: private, max-age=31536000, immutable`, `ETag` fort `"<sha256>:<variante>"` (`variante` = `format` pour l'original, `aac` pour la variante allégée), `Last-Modified` (mtime du fichier). `If-None-Match` qui correspond (valeur exacte, liste ou `*`, même avec `Range`) répond 304 sans corps ; un `If-Range` différent de l'ETag courant (une date compte comme une différence) fait ignorer `Range` et renvoie 200 complet. Les pochettes portant `?v=` (l'URL change avec `updatedAt`) sont `immutable` aussi. Variante allégée : `?q=light` sert `DATA_DIR/media/<id>/stream.m4a` (AAC 192 kbit/s, `audio/mp4`, ETag `:aac`) si `tracks.aac_size_bytes` n'est pas `NULL` et que le fichier existe, sinon l'original (repli silencieux, servi en `Cache-Control: private, no-cache` : l'URL `?q=light` peut répondre autrement une fois la variante prête, alors que la variante et l'URL sans `q` restent `immutable`) ; toute autre valeur de `q` sert l'original. `media/transcode.ts` (`encodeAac`, `convertWavToFlac`, binaire `FFMPEG_PATH`, jamais d'exception : `false` et journal) produit les deux. Une réponse 416 est `no-store`. Pendant une conversion WAV vers FLAC, un flux déjà ouvert continue sur l'ancien inode ; une nouvelle requête `Range` sur la même URL reçoit le FLAC (ETag différent, le navigateur recharge) ; si le fichier a disparu entre la lecture de la ligne et le `stat`, la route relit la ligne une fois avant de répondre 404. `immutable` un an côté navigateur : le cache HTTP du profil survit à la déconnexion, mais toute nouvelle requête reste protégée par la session. Migration 8 : `aac_size_bytes` et `aac_attempted_at` (`NULL` = jamais tentée ; taille `NULL` avec date = échec), `updated_at` n'est pas modifié. Conversion WAV vers FLAC : à l'import, un WAV est converti sans perte en FLAC (le SHA-256 reste celui du fichier déposé ; en cas d'échec le WAV est publié tel quel). Passe d'optimisation : même mécanique paresseuse que le rattrapage de loudness (un titre à la fois sur la chaîne des imports, une seule passe), elle convertit les WAV du catalogue existant (encodage, contrôle du format, `rename` vers `original.flac`, mise à jour de la ligne, puis suppression du WAV) puis encode la variante AAC des titres jamais tentés (`aac_attempted_at IS NULL`) ; chaque titre est traité sous le verrou par titre (`createTrackLocks`, la même instance que les routes admin, passée par `main.ts` et `createApp`), un `original.wav` résiduel à côté d'une ligne FLAC est supprimé, et une variante AAC qui n'est pas plus petite que l'original est supprimée (`aac_size_bytes = NULL`, tentative enregistrée). Un échec pose quand même `aac_attempted_at` : il n'est pas rejoué automatiquement. Reprise manuelle : le bouton (`POST /api/admin/media/optimize`) remet d'abord `aac_attempted_at` à `NULL` pour les titres prêts en WAV ou sans variante, puis démarre la passe ; il est actif si `pending`, `wav` ou `failed` est non nul. La ligne d'état se rafraîchit toutes les 2 s pendant une passe, toutes les 10 s sinon (panneau ouvert). Elle démarre depuis l'onglet Catalogue (« Préparer les titres restants », ligne « Lecture allégée : n titres sur m prêts ») et d'elle-même après chaque import réussi si ffmpeg est disponible (sans événement admin). Côté lecteur, `lib/quality.ts` et le bouton « Qualité : Auto / Max / Allégée » (`player.quality.v1`) choisissent la variante demandée (`auto` : allégée en mode économie de données, réseau lent ou petit écran tactile) ; un changement s'applique au titre suivant. Reverse proxy : laisser passer `Range`, `If-None-Match` et `If-Range` sans les réécrire, et ne pas mettre ces réponses en cache côté proxy (elles sont `private`, propres à la session).

Entretien et santé : `server/src/admin/maintenance.ts` fait une passe qui supprime les répertoires `media/<id>` sans ligne `tracks` et les réceptions `incoming/<importId>` sans import `processing`, à trois conditions : nom UUID (sinon ignoré et journalisé une fois par passe), âge supérieur au délai de grâce `MAINTENANCE_GRACE_MS` (1 h, `mtime` du répertoire et de ses enfants directs, car un fichier est publié avant sa ligne), et requête fraîche confirmant l'absence de ligne juste avant la suppression (un listing en échec est journalisé `maintenance.list_failed` et la passe continue) ; elle purge aussi les lignes `imports` `failed` de plus de 30 jours ou `ready` de plus de 90 jours (jamais les `processing`). Une erreur de suppression est journalisée (`maintenance.remove_failed`) et n'interrompt pas la passe ; un seul passage à la fois (un second appel reçoit le résultat de la passe en cours). Planification : une passe au démarrage (lancée sans être attendue, après `serve()`), puis toutes les `MAINTENANCE_INTERVAL_HOURS` heures (24 par défaut, `0` désactive). La santé est en deux niveaux : `check()` (léger : migrations et `statfs` du `DATA_DIR` couru contre un minuteur de 2 s, ni comptages ni ffmpeg) alimente `/healthz`, public, `200 ok` ou `503 degraded` (migrations en attente, espace libre sous `MIN_FREE_MB`, 500 par défaut, `DATA_DIR` inaccessible ou erreur de base, jamais un 500) ; le `HEALTHCHECK` Docker s'appuie sur ce code. `degraded` signifie « alerter, ne pas redémarrer » : une sonde de vivacité ne doit pas pointer sur `/healthz` (disponibilité et alerte seulement). `evaluate()` (détail complet, test ffmpeg négatif mis en cache 5 minutes) alimente `GET /api/admin/health` pour les admins ; l'onglet Catalogue affiche la ligne « Système » (version, espace libre, migrations, raisons en rouge si dégradé) et la ligne « Entretien » avec le bouton « Lancer l'entretien ».

Import asynchrone : `POST /api/admin/imports` (multipart) écrit le fichier dans `incoming/<importId>/`, crée une ligne `imports` à l'état `processing` et répond 202 avec `importId`. Le worker la passe à `ready` (avec `trackId`) ou `failed` avec `error.reason` : `duplicate`, `unsupported_format` ou `internal`. Le panneau suit les imports avec `GET /api/admin/imports` et `/:id`.

Imports vers un dossier et par URL (migration `id: 6`) : `imports` gagne `folder_id` (`REFERENCES folders(id) ON DELETE SET NULL`) et `source_url` (`NULL` pour un envoi de fichier). La file passe `folderId` à `ingestFile` si le dossier existe encore à l'insertion, sinon `null` (boîte de réception). `POST /api/admin/imports/url` crée la ligne tout de suite (`filename` : dernier segment du chemin, nettoyé en `[^\w.-]` -> `_`, 120 caractères, `download` par défaut). Le téléchargement (`media/download.ts`, `downloadToFile`) se fait hors de la chaîne sérialisée, 2 à la fois (sémaphore, les autres attendent), dans `incoming/<importId>/upload.bin`, puis l'import suit la chaîne comme un envoi classique. Garde-fous : `https:` seulement, adresses publiques seulement (`pinnedFetch` et `createCheckedLookup` de `metadata/fetch-guard.ts`, y compris après redirection), 2 redirections au plus, `Content-Length` et flux plafonnés à `maxUploadBytes`, délai de connexion 20 s, durée totale 15 min, aucune liste blanche d'hôtes. Un échec passe l'import à `failed` (`download_failed`), supprime `incoming/<importId>/` et journalise `import.download_failed` (hôte seulement, jamais l'URL complète) ; `recoverStaleImports` traite un téléchargement interrompu comme un import interrompu.

Dépôt de dossiers (client) : `lib/drop-entries.ts` parcourt les entrées déposées (`webkitGetAsEntry`) sur 8 niveaux au plus et 500 fichiers au plus (au-delà : bannière « Trop de fichiers (500 max) », rien n'est envoyé) ; seuls `.flac`, `.mp3` et `.wav` (casse ignorée) sont gardés, les fichiers cachés sont ignorés. Le bouton « Importer un dossier » (`webkitdirectory`) suit les mêmes règles. `lib/folder-plan.ts` (`planFolders`) déduit des chemins relatifs les dossiers à créer en réutilisant ceux qui existent ; le hook les crée en séquence (409 `folder_conflict` : relecture de l'arbre) avant d'envoyer chaque fichier avec son `folderId`.

Édition par lot : `batch` applique `applyTrackPatch` titre par titre sous le verrou du titre ; un échec interne n'interrompt pas les autres (`failed`). Une ligne `admin_events` par lot, sans titres : `track_batch_update { count, keys }` et `track_batch_delete { count }`.

Pochette proposée par un fournisseur : l'URL vient du cache de propositions, jamais du client. `fetch-guard.ts` n'accepte que HTTPS et une liste de domaines (`COVER_HOSTS`), résout le DNS et refuse toute adresse privée, boucle locale, lien local ou réservée, épingle la connexion sur les adresses vérifiées, suit au plus 2 redirections (revalidées à chaque saut), plafonne le corps à 5 Mio et vérifie la signature JPEG/PNG/WebP. Un refus donne `cover_rejected` (422) : le texte de la proposition est déjà appliqué et la réponse contient le titre mis à jour (`track`, `coverApplied: false`).

Front d'administration : `components/admin/*` (`admin-panel`, `folder-tree`, `track-table`, `track-editor`, `metadata-dialog`, `upload-zone`, `context-menu`), `lib/admin-api.ts` (appels typés, en-tête CSRF), `lib/import-queue.ts` (file côté client : envoi en série, refus des fichiers trop gros d'après `GET /api/admin/limits`, suivi de l'état serveur) et `lib/hooks/use-import-queue.ts`. Une pochette remplacée change `updatedAt` du titre ; l'URL de pochette porte `?v=<updatedAt>` pour contourner le cache.

| `GET /api/admin/requests`             | admin   | `{ requests }` avec `requestedBy` : en attente puis validées, 200 au plus.                                                                                             |
| `POST /api/admin/requests/:id/accept` | admin   | `{ request }`. 404 `request_not_found`, 409 `request_not_pending`. Événement `request_accept`.                                                                         |
| `POST /api/admin/requests/:id/reject` | admin   | `{ reason? }` (200 caractères au plus), `{ request }`. 404 `request_not_found`, 409 `request_not_pending` (déjà `added` ou `rejected`). Événement `request_reject`.    |
| `DELETE /api/admin/requests/:id`      | admin   | 204 ; 404 `request_not_found`. Événement `request_delete`.                                                                                                             |

Table `song_requests` (migration `id: 3`, reconstruite par la migration `id: 7`) :

| Colonne                      | Type et contrainte                                          |
| ---------------------------- | ----------------------------------------------------------- |
| `id`                         | `TEXT PRIMARY KEY`                                          |
| `user_id`                    | `TEXT NOT NULL`, référence `users(id)` `ON DELETE CASCADE`  |
| `title`, `artist`            | `TEXT NOT NULL` (`artist` vaut `''` par défaut)             |
| `album`, `year`, `cover_url` | `TEXT`, `INTEGER`, `TEXT` nullables                         |
| `source`                     | `musicbrainz`, `deezer`, `itunes` ou `manual`               |
| `status`                     | `pending` (défaut), `accepted`, `added` ou `rejected`       |
| `track_id`                   | `TEXT` nullable, `REFERENCES tracks(id) ON DELETE SET NULL` |
| `reject_reason`              | `TEXT` nullable (200 caractères au plus)                    |
| `created_at`, `updated_at`   | `TEXT NOT NULL`                                             |

Index : `song_requests_status_created(status, created_at)` et `song_requests_user(user_id)`. `cover_url` vient toujours du cache de propositions, jamais du client. Les mutations admin écrivent `request_accept`, `request_reject`, `request_fulfilled` (`{ requestId, trackId }`) et `request_delete` dans `admin_events`.

Cycle de vie (migration `id: 7`) : `pending` -> `accepted` (optionnel) -> `added`, ou `pending`/`accepted` -> `rejected`. SQLite ne modifiant pas un `CHECK`, la migration reconstruit `song_requests` (mêmes colonnes plus `track_id` et `reject_reason`, lignes copiées, index recréés) et ajoute `imports.request_id` (`REFERENCES song_requests(id) ON DELETE SET NULL`). Un import lié à une demande (champ multipart `requestId`) applique à la fin, quand il est `ready`, le titre, l'artiste et l'album de la demande (non vides : ils priment sur les tags), télécharge la pochette de la demande (`guardedFetchImage`) et ne l'applique que si le fichier n'en a pas d'intégrée (un échec est journalisé `request.cover_failed` sans rien bloquer), puis passe la demande à `added` avec `track_id`. Un import `duplicate` passe aussi la demande à `added` avec le titre existant ; `unsupported` ou `internal` la laissent telle quelle. Côté lecteur, le badge de nouveautés compte les demandes de l'utilisateur non `pending` modifiées depuis la dernière ouverture du modal (clé `localStorage` `player.requests.seen.v1:<userId>`, une par utilisateur, écrite à l'ouverture et à la fermeture du modal). L'exécution d'une demande ne renseigne que la ligne du catalogue (titre, artiste, album, pochette) et ne réécrit pas les tags du fichier ; une modification ultérieure du titre dans l'éditeur les réécrit.

Sans session : 401 `session_required` (ou `session_expired`). Session sans le groupe admin sur `/api/admin/*` : 403 `admin_required`. Toute autre route `/api/*` : 404 `not_found`. Les routes de métadonnées ne sont montées que si le serveur a un moteur de recherche (toujours le cas via `main.ts`).

## Performance

| Poste               | Choix                                                                                                                                                                                                                      |
| ------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Fond WebGL          | 30 i/s à la demande, pause quand l'onglet est caché, uniforms mutés sans React, chunk différé (`React.lazy`).                                                                                                              |
| Flou d'arrière-plan | Seules les cartes ont un `backdrop-filter` ; les boutons à l'intérieur n'en ont plus (même rendu, un calque de flou en moins chacun). En mode visualiseur agrandi, plus aucun flou et le reste de l'interface est démonté. |
| Visualiseur         | Un seul `fill()` par image, taille suivie par `ResizeObserver`, `requestAnimationFrame` annulé au démontage.                                                                                                               |
| Animations          | `LazyMotion` + composants `m`, fonctionnalités chargées à la demande (`lib/motion-features.ts`).                                                                                                                           |
| Images              | Dimensions explicites, `decoding="async"`, `loading="lazy"` dans la file d'attente.                                                                                                                                        |
| Pré-chargement      | Un second élément audio charge le titre suivant pendant la lecture ; au changement de piste les deux éléments sont échangés, sans dépendre du cache HTTP.                                                                  |

## Chorégraphie d'un changement de piste

Constantes dans `lib/transitions.ts`. Ordre garanti : fond, puis carte, puis notification.

| Instant | Élément       | Détail                                                                                        |
| ------- | ------------- | --------------------------------------------------------------------------------------------- |
| 0 ms    | Gradient      | Fondu de couleurs sur 1000 ms (`useSongGradient`, interpolation RVB à ~30 i/s).               |
| 150 ms  | Carte lecteur | Pochette, titre et artiste sortent puis entrent (350 ms).                                     |
| 450 ms  | Notification  | `NotificationManager` retarde la notification de piste ; un second skip annule la précédente. |

Côté moteur, si le titre suivant est déjà pré-chargé, `MusicManager` échange l'élément audio actif et l'élément de pré-chargement au lieu de recharger la source ; le changement est donc quasi instantané.

## Media Session et reprise

- Media Session : `navigator.mediaSession` expose le titre, l'artiste, l'album et la pochette du titre courant, l'état de lecture, la position, et les actions lecture, pause, précédent, suivant et déplacement (`lib/media-session.ts`). Les touches multimédia et l'écran de verrouillage pilotent donc le lecteur.
- Reprise : `lib/resume-state.ts` enregistre le titre et la position dans `localStorage` sous la clé `player.resume.v1` (toutes les 2 s). Au chargement, le lecteur se replace sur ce titre, en pause. L'état est ignoré au-delà de 30 jours ou si le titre a disparu du catalogue ; une position sous 5 s redémarre le titre à 0.

## Développement

`yarn dev` lance trois processus : Vite (`http://localhost:3000`, qui proxifie `/api` vers l'API), l'API (`http://localhost:8080`, configurée par `.env.development`) et un fournisseur OIDC factice (`http://localhost:3002`, `server/dev/mock-oidc.ts`). Le navigateur ne parle qu'à `:3000` : `APP_URL` vaut donc `http://localhost:3000` et le callback OIDC revient par le proxy.

Pour tester la connexion, ouvrir `http://localhost:3000/api/auth/login` puis se connecter avec l'un des comptes (n'importe quel mot de passe) :

| Compte        | Groupes     |
| ------------- | ----------- |
| `admin@test`  | `["admin"]` |
| `user@test`   | `["users"]` |
| `nobody@test` | `[]`        |

`GET /api/session` renvoie ensuite le rôle déduit des groupes.

Quand `DEV_BYPASS_LOGIN=true` (activé dans `.env.development`), l'écran de connexion de test propose « Entrer en admin » et « Entrer en user », qui ouvrent une session sans passer par le fournisseur OIDC, avec les identités `dev-admin` / `dev-user` (émetteur `dev-bypass`). Ces sessions ne sont pas revérifiées auprès du fournisseur. Le serveur refuse de démarrer si `DEV_BYPASS_LOGIN=true` avec `NODE_ENV=production`.

Le fournisseur factice expose des routes de contrôle : `GET /mock/accounts` liste l'état des comptes, et `POST /mock/accounts/:id` avec un corps JSON `{ "groups": [...], "disabled": true }` modifie les groupes ou désactive un compte (le prochain rafraîchissement de session échoue). Exemple :

```sh
curl -X POST localhost:3002/mock/accounts/user@test -H 'content-type: application/json' -d '{"groups":["admin"]}'
```

`.env.development` est versionné : il ne contient aucun secret réel (clé de session et client OIDC propres au développement). Le dossier `.data/` (données de l'API) est ignoré par git.
